# Step 1.5：轻验证 — 强制关卡

## 规则

没有验证过思路的用户，**不能进入Step 2定方案**。

## 为什么必须有这一步？

大多数项目失败不是因为执行差，是因为**前提假设是错的**。在投入3个月开发前，必须用0成本方式验证"这个问题真的能用AI解决"。

## 验证问题（必须问）

用户说"我想用AI做X"，你必须问：

> "你用现有工具验证过这个思路能跑通吗？哪怕是用ChatGPT/Claude手动跑一次，看看输出质量？"

## 验证结论分类处理

| 用户回答 | 处理 | 能否进Step 2 |
|---------|------|-------------|
| "我试过GPT-4o转写，效果还行" | 追问：试了多少场？效果好的标准是什么？有没有截图/记录？ | ✅ 记录验证结论 |
| "没试过，但我觉得能行" | ❌ 强制要求0成本实验："这是进入下一步的前提。你先拿一段真实数据，用任意AI工具跑一遍，15分钟的事。有了结论我们再聊。" | ❌ 不能进 |
| "试了，效果不行" | ✅ 追问：哪里不行？是转写不准、结构提取不对、还是待办识别不了？这个信息比"效果好"更有价值 | ✅ 记录失败结论 |
| "试了，效果还行，但..." | ✅ 追问"但"后面的内容——这才是真正的边界条件 | ✅ 记录完整结论 |

## 更新骨架

```
## [ ] 已有验证成果
- [ ] 验证方式：（手动测试/竞品调研/用户访谈/数据挖掘/未验证）
- [ ] 验证结论：（效果达标/效果不达标/部分达标-需说明）
- [ ] 关键发现：（具体发现了什么，包括失败的细节）
- [ ] 下一步验证计划：（如果当前验证不充分，什么时候补）
```

## 关键原则

验证可以粗糙，但不能没有。一个做了粗糙验证的项目，比一个"想法很完美但没验过"的项目更值得立项。
